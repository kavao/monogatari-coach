# 章末ステータスと本文内の通知

このガイドを読むと、作品ごとに「ゲーム的なステータスを章末に出すか」を決め、本文の章末ブロックや本文の途中の通知（天の声・神の告知・ステータス窓など）を Monogatari Coach に書かせ、Web 投稿稿や紙書籍の proof に出せるようになります。

## TL;DR

- 作品の `config.md` に `CHAPTER_STATUS` 行を置きます。値は `OFF` / `SYNOPSIS` / `TEXT` の三つで、**行がなければ `SYNOPSIS`**（あらすじ・設計の章末にだけ出し、本文には出さない）です。
- 本文の章末にも出したい作品は `TEXT` にし、型（`CHAPTER_STATUS_STYLE`）を一つ選びます。基準は転生ものの「天の声」型の通知（通知ログ型）です。
- 本文の途中の通知は、`CHAPTER_STATUS` とは別に、作品の `status_display.md` で「誰が・どう告げるか」を決めたときだけ書かれます。
- 本文の地の文・台詞には、決めていない数値のステータス（「好感度が25/100になった」など）は書かれません。

## このガイドを使う場面

1. **どんな場面で使うか** — 異世界・迷宮・ゲームなどで、成長や獲得をステータスとして見せたいとき。神の告知やシステムの通知を本文に出したいとき。以前の作品の章末にあるまとめの扱いを決めたいとき。
2. **チャットへの指示文** — 次の一言で動きます。

   ```text
   この作品は章末にステータスを出したい。
   ```

   と入力すると、Monogatari Coach は自動的に型の候補を示し、選んだ型で `status_display.md` を作り、`config.md` に `CHAPTER_STATUS | TEXT` を書きます。本文内の通知も使いたいときは「神様が話しかけてくる通知も入れたい」のように、出方を一言添えます。Monogatari Coach は §3 の表の空欄を質問で埋めます。
3. **Monogatari Coach が行うこと**
   - 執筆の前に `config.md` と `status_display.md` を読み、定義のない数値を本文に書かない。
   - 章が完成したら、最後のファイルの末尾に章末ブロックを置き、台帳に値を記録する。
   - 清書・追記でブロックと定義どおりの通知を消さない。
   - 一貫性監査で、ブロック・台帳・設計の値を照らし合わせる。
4. **ユーザーが確認できるもの** — 作品フォルダの `status_display.md`（書式・項目・通知・台帳）、本文の章末の `<!-- status:begin -->` から `<!-- status:end -->` まで、`novel_project_check.py` の出力の「章末ステータス:」の行。

## 1. 三つの値

| 値 | あらすじ・設計の章末 | 本文の章末 | 本文の地の文・台詞 |
|---|---|---|---|
| `OFF` | 出さない（変化は章の出来事の文に溶かす） | 出さない | 数値を書かない |
| `SYNOPSIS`（既定） | 「状態変化・関係変化」欄を置く（数値を書いてよい） | 出さない | 数値を書かない |
| `TEXT` | 同上（本文のブロックの元になる） | 印で囲んだブロックを一つ置く | 数値を書かない |

新しく作品を起こすと、Monogatari Coach は `config.md` に `| CHAPTER_STATUS | SYNOPSIS |` を書きます。異世界・迷宮・ゲームの作品では、企画の最初に「本文の章末にも出せます」と型の候補を2〜3個示します。選ぶかどうかは作者が決めます（返事がなければ `SYNOPSIS` のまま）。

## 2. 型を選ぶ

型は章末ブロックの書式です。テンプレートと記入例は [`_how_to.example/status_display.md`](../../_how_to.example/status_display.md) にあります。

| ID | 型 | 中身 |
|---|---|---|
| `notice_log`（基準） | 通知ログ型 | 獲得・進化・称号を、声やシステムの告知として一行ずつ並べる |
| `status_window` | ステータス窓型 | 名前・種族・レベル・能力値・スキルを一覧の窓で示す |
| `diff` | 差分型 | 章で動いた値だけを「旧 → 新」で示す |
| `experience_log` | 経験ログ型 | 人物ごとに、経験したことと変わったことを数値なしで示す |
| `card` | 鑑定書・ギルドカード型 | 作中の書類や鑑定の結果として示す |

型を決めたら、作品フォルダに `status_display.md` を作ります。葉のテンプレートが写され、作品向けに書き換えて使います（写したあとは、葉を改訂しても作品側は変わりません）。

作品の status_display.md を作るコマンドです。`--notice` は本文内の通知の演出の例を一緒に写すときだけ付けます。

```bash
# 通知ログ型で作り、本文内の通知は「天の声」の例を写す
uv run python tools/novel_status_display.py init novels/050_作品名 --style notice_log --notice heaven_voice
```

実行後、`novels/050_作品名/status_display.md` ができます。既にある場合は上書きしません。

続けて `config.md` の「## 基本情報」の表に次の2行を書きます。

```text
| CHAPTER_STATUS | TEXT |
| CHAPTER_STATUS_STYLE | notice_log |
```

## 3. 本文内の通知を決める

本文の途中に出る通知は、作品によって前提がまったく違います（神が話しかけてくる、ステータス窓が開く、戦闘中に文字が流れ続ける、鑑定したときだけ結果が浮かぶ、など）。そのため共通の決まりや上限はなく、`status_display.md` の「本文内の通知」の表で作品ごとに決めます。

| 項目 | 決めること |
|---|---|
| 使うか | 使う / 使わない |
| 主体 | 誰・何が告げるか（神、世界の声、システム、スキル、道具） |
| 出方 | 声で告げる、窓が開く、文字が流れる、結果が浮かぶ |
| 届く範囲 | 本人だけ、その場の全員など |
| きっかけ | 獲得・進化、鑑定、主体の気まぐれなど |
| やりとり | 告げるだけか、人物と話せるか |
| 置き方 | 独立した行にするか、地の文・台詞に織り込むか |
| 書式 | 括弧・記号・口調 |
| 括弧 | 機械が読む括弧（例 `《》`）。この中の数値は「本文に数値を書いた」候補から外れる |
| 頻度の方針 | 「転機だけ」「戦闘中は流し続ける」など |

- 一つでも空欄があると、Monogatari Coach はその作品で本文内の通知を書きません。
- 章末ブロックは出さず、本文内の通知だけを使う作品は、`CHAPTER_STATUS` を `SYNOPSIS` のままにして、この表だけを埋めます。
- 主体に名前を付けるときは、`world.md` の用語にも登録します。人物と話せる主体は `character.md` にも置きます。

## 4. 本文ではどう書かれるか

`TEXT` の作品では、章が完成したときに、章の最後のファイルの末尾へ次のようなブロックが置かれます。

```markdown
　ミナトは手すりをつかみ、遠い水平線の色が変わるのを見た。

<!-- status:begin -->
《記録》灯台の声より通知
・技能「潮読み」を得た
・夜目が第二段階に至った
<!-- status:end -->
```

- 一章に一つです。章が `novel_text03_1.md`・`novel_text03_2.md` のように分かれていれば、いちばん後ろのファイルにだけ置かれます。
- ブロックと、本文内の通知の独立した行（行頭に `<!-- status:line -->`）は、字数・句読点の測定に入りません。分量の目安や清書の削減率は、これらを除いて測られます。
- 追記や場面の書き直しは、ブロックの手前に入ります。清書でもブロックと定義どおりの通知は消えません。
- ブロックの値は `status_display.md` の「台帳」に章ごとに記録され、一貫性監査で本文と照らし合わされます。

章が完成したときに Monogatari Coach が実行する確認です。手で実行してもかまいません。

```bash
# 第3章のブロックがそろっているかを確かめる（重複・置き場・欠落・台帳の値）
uv run python tools/novel_status_display.py check novels/050_作品名 --completed-chapter 3
```

終了コード 0 なら問題ありません。ブロックの行に台帳の項目名があるのに値が台帳と違うとき（台帳は `HP 50`、ブロックは `HP 100` など）は、警告（`!`）が出ます。項目名がブロックに出ていない値や、数値でない経験の記述が台帳と同じ意味かどうかは、一貫性監査で確かめます。

### 完成した章に項を足したとき

最後のファイルが変わるので、ブロックを新しい最後のファイルへ移します。Monogatari Coach が作者に確かめてから次のコマンドで移します。途中で止まっても、同じコマンドで続きから再開できます。再開したときに、移動先のブロックが見つからない、または移動元・移動先に記録と違うブロックがある（止まっているあいだに書き換わった）とき、移動元から外したはずのブロックが戻っているときは、どちらのファイルにも書き込まずに止まり、エラーを表示します。

```bash
# 第3章のブロックを最後のファイルへ移す（止まったら同じコマンドで再開）
uv run python tools/novel_status_display.py move novels/050_作品名 --chapter 3
```

METRON が ON の作品では、ブロックの書き換えは執筆接続（writing_bridge）の `status_block` の run を通して行われます。こうすると本文が「計測が古い」にならずに済みます。run を準備したあとに本文が変わった場合（別の run でブロックを更新したなど）は保存されないので、新しい run で準備し直します。通常の場面の書き直しの候補に章末ブロックの印が入っていると、受け取りの時点で止まります。

## 5. 投稿・出版に出す

Web 投稿稿は、印だけを外した稿を `_novel_text_re/` に書き出してから使います。

```bash
# 確認（dry-run）— 書き出すファイルを表示する
uv run python tools/novel_web_export.py novels/050_作品名 --dry-run

# 本番（既存の _novel_text_re は上書きしない）
uv run python tools/novel_web_export.py novels/050_作品名

# 書き直すとき（旧版を _novel_text_re/_old/<日時>/ へ退避してから上書き）
uv run python tools/novel_web_export.py novels/050_作品名 --overwrite
```

カクヨムのルビ変換を使う作品は、このあとに `_novel_text_re` を入力にしてルビ変換を重ねます（[ユーザスキルと雛形の置き場](user-skills.md) の kakuyomu-convert）。

紙書籍の proof（[紙書籍 proof PDF](paper-proof-export.md)）では、ブロックは小さめの字で天から2字下げ、前後に細い罫を引いて描かれます。罫はブロックの文字の高さまでで、罫だけがページに残らないように改ページします。独立した通知の行は、罫なしで同じ字下げになります。

## 6. 以前からある作品

`config.md` に行のない作品は `SYNOPSIS` として扱われます。本文の章末に印のない旧形式のまとめ（`---` のあとの「**ボディーの変化・経験ログ**」のような箇条書きなど）がある作品では、`novel_project_check.py` が INFO を出します。本文は自動で書き換えられません。

- 本文に残すなら、`CHAPTER_STATUS | TEXT` と `CHAPTER_STATUS_STYLE | experience_log` を書き、Monogatari Coach に「旧形式の章末ブロックに印を付け直して」と頼みます（清書の手順で旧版を退避してから直します）。
- 残さないなら、内容をあらすじ・設計の章末の欄へ移すよう頼みます。
