# ルール作成規約

Monogatari Coach のルールを増やすときは、本文を足す前に「何をどこへ置くか」を決める。
同じ必須条件を複数箇所へ長文で書かず、概念正本・スキル・docs・創作技法の役割を分ける。

## 1. 最初に分類する

新しい記述を追加するときは、次のどれに当たるかを先に決める。

| 分類 | 置き場 | 内容 |
|------|--------|------|
| 概念 | `.rulesync/rules/concepts.md` | 複数モード・複数スキルにまたがる短い定義、禁止、完了条件 |
| 行動規範 | `.rulesync/rules/*.md` | エージェント全体へ常時適用する判断ルール |
| スキル手順 | `.rulesync/skills/<skill_name>/SKILL.md` | 特定作業でエージェントが実行する手順・確認事項 |
| 操作説明 | `docs/**/*.md` | 人間が読むコマンド例、手順、トラブルシュート |
| 創作技法 | `_how_to.example/**/*.md` | 小説・漫画・タグ・書評など「どう書くか」の雛形・基準 |
| ユーザー調整 | `_how_to/**/*.md` | ユーザーが直接調整する技法メモ。明示依頼なしに恒久ルールを書かない |

## 2. 正本を一つに決める

- 事故防止に関わる必須条件は、まず `concepts.md` に短く置く。
- スキルには、その概念を当該作業でどう適用するかだけを書く。
- `docs/` には、人間がどう操作し、何を確認できるかを書く。
- `_how_to.example/` には、創作技法としての基準だけを書く。
- `AGENTS.md` / `CLAUDE.md` は LLM 別入口であり、主編集先にしない。

### 2.1 ローカル調整と標準データの扱い

- ルールを新規作成・変更・更新するときは、ユーザーから別途指定がない限り、`_how_to/` のローカル調整を公式ルールの既定動作・必須条件へ取り込まない。
- 公式ルールの基準は **`_how_to.example/` の標準データ・標準構造**とする。ローカル側にのみ存在する語彙、項目、運用差分は、公式ルールの根拠にしない。
- `_how_to/` の内容を公式ルールへ昇格したい場合は、ユーザーの明示指定を受けたうえで、必要に応じて先に `_how_to.example/` の標準データへ反映し、その標準をもとに `.rulesync/` を更新する。
- ローカル調整を参照した場合でも、標準データと異なる部分は公式ルールへ混入させず、ユーザー固有の調整として扱う。

## 3. 重複を避ける

同じ概念を複数箇所に置くときは、次の形にする。

1. `concepts.md` に短い正本を書く。
2. `overview.md` には概要と参照先だけを書く。
3. スキルには作業固有の適用手順だけを書く。
4. `docs/` には長い例、コマンド、背景説明を書く。

禁止:

- 同じ「禁止」「完了条件」「優先順位」を、複数ファイルへ別表現で長文複製する。
- スキルに provider 別の長い辞書や大量の実行例をため込む。
- `docs/` に LLM の内部行動指示を主目的として書く。
- `_how_to/` に、ユーザーの明示依頼なしでツール運用ルールを書き込む。
- **エージェントの必須条件・完了条件を `_how_to/` のファイル名・見出し番号・節名に依存させる**（例: 「`_how_to/tag.md` §3 に従う」だけで Tag Mode を完結させない）。横断の必須 ID・汎用／カスタムの分離は **`workflow-specification.md`** と **作品 `_meta.md`** に自己完結で書く。短い完了条件は **`concepts.md`** に残す。`_how_to/` は創作技法の任意参照に留める。

## 4. ルール追加時のチェックリスト

ルール・スキル・docs を追加または更新する前に確認する。

- これは概念、行動規範、スキル手順、操作説明、創作技法のどれか。
- 同種の概念が `concepts.md` または既存スキルにないか。
- 事故防止の核は `concepts.md` に置けるか。
- 長い例、コマンド、エラー例は `docs/` に逃がせるか。
- 新しいスキルを追加した場合、対応する `docs/` の説明ページまたは索引リンクを追加したか。追加しない場合、その理由を査証ログに残せるか。
- 正本と副本の関係を明示したか。
- rulesync 生成物を直接主編集していないか。
- 変更後に必要なら `rulesync generate` を実行し、入口ファイルの差分を確認するか。
- セッション末尾に査証ログへ、正本・派生先・次の作業を追記するか。

## 5. rulesync の扱い

`rulesync` は正本ではなく、`.rulesync/` 配下の正本を LLM 別入口へ配布する生成・同期レイヤーとして扱う。

- 主編集先: `.rulesync/rules/`、`.rulesync/skills/`
- 生成・入口: `AGENTS.md`、`CLAUDE.md` など
- 入口ファイルの内容を変えたい場合は、先に `.rulesync/` 側を直す。
- 生成後は、入口ファイルに意図しない肥大化や欠落がないか確認する。

## 6. 小さく改修する

既存の大きなルールを整理するときは、概念単位で分けて進める。

1. 新しい正本を作る。
2. 既存本文を参照に置き換える。
3. スキルの手順を薄くする。
4. docs へ詳細を移す。
5. rulesync 生成物を同期する。

一度に大幅削除せず、各段階で差分と査証ログを確認する。
