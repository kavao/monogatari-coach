## 目的

goal モードは、完了条件を書いた依頼を一度渡し、複数の手順を続けて実行させる使い方である。自律実行でも、既存の承認ゲートと第0層は緩和しない。このスキルは、goal の受け方・止まり方・報告のしかたと、ヘルプ（goal 文の雛形提示）を定める。人間向けの説明と実装例は `docs/workflow/goal-mode.md`。

## 開始時

1. goal 文から「対象（作品・章・場面）」「完了条件」「触ってよい範囲」「事前承認」を抜き出す。
2. 完了条件が、ファイルの存在・ツールの結果（`novel_char_count.py`、`novel_project_check.py`、`writing_bridge` の `report.json` など）で確認できない場合は、確認できる形に言い換えて1回だけユーザーへ尋ねる。尋ねられない環境では、言い換えた条件を報告の冒頭に明記して進める。
3. `novel_status.py <作品> --next` と `novel_project_check.py` で現在地を確認し、不足があれば先に報告する。対象に合うスキル（`concepts.md` のルーティング）を読み込む。
4. 触ってよい範囲の外のファイルは変更しない。範囲が書かれていなければ、依頼された章・場面と `_meta.md` だけとする。

## 実行中

- 各スキルの手順と承認ゲートに従う。goal が「最後まで」と言っても、ゲートを飛ばさない。
- **事前承認**は goal 文に明記された項目だけ有効とする。記録欄（`--authorization` など）には goal 文の該当箇所を引用する。範囲を広げて解釈しない。
- 事前承認で外せるのは、作品の設計や本文に関するユーザー確認（子エピソードの追加案、引き締め・収束の採用、保存前の確認など）に限る。次は goal 文に書かれていても、第0層の規則5に従い明示された範囲でだけ実行する: git add / commit / push、外部送信、課金を伴う本番生成、秘密情報の扱い。
- 承認が要る箇所に当たったら、その作業だけを保留し、案または差分を提示して「保留中」として記録する。独立した作業（ほかの章の評価など）は続けてよい。同じ場面を直接編集と `publish` の両方で書かない。
- 区切りで `_meta.md` の次回タスクを更新する。会話が要約されたら、`_meta.md` の「現在のフェーズ」と「次回タスク」から再構成する。

## 完了報告

次の3点を、チャットの要約として短く返す。成果物の完了は、正本への書込みと再読込または検証のあとにだけ報告する。

1. 達成: 完了条件のうち、確認できたもの（確認に使ったツールと結果）
2. 保留: 承認待ち・止めた理由・再開に必要な返答
3. 次の一手: 次に頼むとよい goal 文の案

査証ログへ、依頼の要約・保留事項・次の作業を追記する（`workspace-audit-log`、AUDIT_LOG が OFF の作品を除く）。

## ヘルプ（goal 文の提示）

「goal モードで頼みたい」「goal 文を作って」と言われたとき:

1. 作品が指定されなければ `novels/` の作品から選んでよいかを尋ねる。
2. `novel_status.py --next` の結果から次の作業を選び、対象・完了条件・触ってよい範囲を埋めた goal 文を1つ提示する。事前承認は、ユーザーが望むと言った場合だけ文に入れる。
3. その作業で止まる箇所を先に伝える。
4. 実装例の一覧は `docs/workflow/goal-mode.md` を案内する。

## 禁止

- 完了条件が未確認のまま「完了」と報告する。
- goal 文にない事前承認を推測して外す。
- 保留を黙って省く、または保留中の作業を承認済みとして進める。
