## 目的

プロットのアレンジで、構造理論の当て方を作業者ごとに変えない。型どおりにすると全作品が同じ色になり、外しすぎると平坦や壊しっぱなしになる。その二律背反を、**壊し方の作法は固定し、いつ・何を壊すかだけを揺らす**ことで吸収する。

- 技法（構造論・流れ破壊・黄金律の型・モードの意味）: `_how_to.example/episode/general/episode_flow_peak_payoff.md`、`episode_flow_break.md`（§7 構造方針）、`episode_golden_structure.md`。作業用 `_how_to/episode/general/` に同名があればそちら。
- 数値の正本: `_how_to.example/episode/general/episode_structure_dosing.json`（`_meta.version` が確率表の版）。実際に使う表の決め方は手順7の「実効の表」で一本化する。
- 計画と経緯: `_workingspace/plans/20261025_structure-theory-dosing.md`。

## 使う場面

- 既存作品で「平板なのでアレンジして」「プロットをもっと変えて」「展開を盛り上げて」「先が読める」「転がほしい」と頼まれた。
- 新規企画の Gate B で章出来事を作るとき（`novel-planning` の B3 から呼ばれる）。
- 「三幕構成で組んで」「Save the Cat で」と型を指定された（`golden`）。

使わない場面: 清書・「わかりやすく」の手直し・規定量調整（出来事を足せない。`concepts.md`「文章の伸縮」）。指定箇所だけの直しを頼まれたとき。

## 創作技法契約との関係

構造論と流れ破壊の2葉は、この作業の**工程正本**である。作品の `_meta.md` の selected に無くても読む。selected は書き換えない。黄金律の葉は `golden` のときだけ読む。完了報告に「工程正本として読んだ葉」を書く。

## 手順

### 1. 作業前の判定

1. `uv run python tools/novel_work_migrate.py novels/<作品> --advise edit` を実行し、結果に従う（`concepts.md`「作品フォルダの機械の記録」）。
2. 作品の `_meta.md`、`design_specification.md`、`config.md`、本文の章構成を読む。2葉を読む。

### 2. モードを決める

優先順位は次のとおり。

1. 今回の依頼での明示（「三幕構成で」→ `golden`、「振らずに直して」→ `diagnose`、「平坦なままでいい」「オチは要らない形式で」→ `none`）。
2. `_meta.md` の Gate B 記録にある **構造方針**。
3. 既定の `rolled`。

1 と 2 が食い違うときは 1 に従い、記録を書き換えるかを作者に一言確かめる。

### 3. 診断する（全モード共通）

章ごとに次の表を作る。値は本文（無ければ設計）を読んで付ける。

| 章 | 持ち味の軸の強さ（0〜3） | 大きな転 | 小さな転 | 先送りの溜まり（0〜2） | 備考 |
| --- | --- | --- | --- | --- | --- |

- 持ち味の軸は、構造論の texture-axis（緊張・居心地・距離など）を作品ごとに一つ決めて書く。
- **平坦な区間**: 強さが2章以上続けて同じ値で、その間に転が無い区間。読み進みの推移で trend がすべて flat の章は、隣の章によらず、その章だけで平坦とする（二つは「または」）。
- **約束**: rank: main の約束ごとに、回収済み・未回収・意図した none を書く。hidden の約束は植え付けの箇所数を書き、2未満なら「植え付け不足」。
- **山**: 構造上の山（PEAK）と感情の最大点（texture-climax）の章を、見せる順で書く。
- **読み進みの推移**（あれば）: `_reader/walk/<session_id>/` の読み進み感想を `uv run python tools/novel_reader_walk_check.py <journal.md> --trace-output <出力.json>` で推移にし、trend がすべて flat の章を平坦の材料に加える（手順6の道具に `--reader-trace` で渡せる）。
- **作品全体の決定**: 作品の約束の破壊（ジャンル転調）の有無、オチの回収のしかた、答えの形、後味について、すでに決まっているかを `_meta.md`・`design_specification.md`・`proposal.md`・本文から確かめ、決まっていれば書かれている箇所を書く。構造方針欄が無いことを「未決」と同じに扱わない。設計や本文に結末があれば決定済みである。

### 4. 変更の範囲を固定する

抽選・案作りの前に、大きな転のある章を分ける。

- **維持**: 今回は動かさない転。
- **見直し**: 移動・置換・削除を検討する転（作者の依頼、または診断の結果）。
- **抽選対象**: 今回アレンジする章。見直しの転があった章も含める。執筆済みの章を含めてよいが、反映は加筆・改稿工程になる（手順9）。維持する転のある章を抽選対象にしても、その章では大きな転も小さな転も振り直さない（初期の C に数え済み。記録には「振らない: 維持する大きな転がある」と残す）。

作品全体の項目（作品の約束の破壊・オチの回収のしかた・答えの形・後味）も、同じく分ける。

- **維持**: 診断で決定済みの項目。作者が見直しを明示しない限り、こちら。「中盤を盛り上げて」のように一部の章だけを頼まれたときは、結末や後味を変えない。
- **見直し**: 作者が今回の見直しを明示した項目（「結末も変えて」「後味を明るく」など）。
- **未決**: 診断でどこにも決まっていなかった項目（新規企画など）。

振るのは見直しと未決の項目だけ。

### 5. モードごとに分ける

| モード | やること |
| --- | --- |
| `rolled` | 手順6〜7で振り、結果から案を作る |
| `golden` | 選んだ型の節目（黄金律の葉の対応表）に転・山があるかを確かめ、欠けた節目について案を作る。振らない |
| `diagnose` | 振らない。診断で見つかった箇所ごとに、流れ破壊のカタログから案を作る |
| `none` | 振らない・転を勧めない。平坦・オチなしが意図どおりかを作者に確かめる。意図なら記録して終わる。意図でなければ、作者の了承を得てモードを変えてやり直す |

### 6. 確率を決める（`rolled`）

**既定は道具で振る。** `tools/novel_structure_draw.py` は、この手順6と手順7（実効の表・`--eval` と同じ抽選・振るたびの記録）をそのまま実装している。手順3〜4の結果を診断の表（JSON）にして渡す。

```text
uv run python tools/novel_structure_draw.py novels/<作品> novels/<作品>/_work/structure/diagnosis_<YYYYMMDD_HHMM>.json
```

- 診断の表は `_work/structure/diagnosis_<YYYYMMDD_HHMM>.json` に保存してから渡す（抽選の再現に要る入力なので残す）。
- 形: `{"seed": W, "total_chars": 字数 または "range": {"L": 下限, "U": 上限}, "band_offset": 既に決めたずらし（無ければ省く）, "chapters": [{"id": "ch01", "strength": 0〜3, "major": 既存の大きな転の型 または null, "major_status": "keep" / "review"（major があるとき）, "minor": true/false, "backlog": 0〜2, "scope": "target" / "outside", "no_remainder": true/false, "foreshadow_before": true/false}], "work_items": {"contract_break" / "payoff_mode" / "payoff_answer" / "ending_tone": "keep" / "review" / "undecided"}}`。章は作品の順にすべて書く（抽選対象でない章も、帯・直前の転・平坦の判定に要る）。
- 読み進みの推移があれば `--reader-trace <推移の JSON>` を付ける。やり直しは `--attempt <回数>`。記録へ書かずに確かめるだけなら `--dry-run`（同じシードなので、本番でも同じ結果になる）。
- 出力（JSON）の `draw_ids`・`chapters`・`work_items`・`shortage`・`shortage_reasons` を案の材料にする。終了コード 2（入力や表の不備）のときは、エラーを直して振り直す。手で値を補って続けない。
- 道具が使えないときだけ、以下の定義どおりに手で振る（手順7）。

以下は道具が実装している定義である。数値は確率表の `補正` から取る。以下の数値は版 `2026-10-25.1` のもの。

**回数の範囲**: 作品の字数（設計の目標字数、無ければ `novel_char_count.py` の合計）から、`回数の範囲` で下限 L・上限 U を決める。作者が「転はいらない」「もっと入れて」と言えば、その場で変えて記録する。

**数える**: 維持する転の数を C とする。見直しの転は C に入れない（案のための計算であり、承認前に旧配置を消すわけではない）。

**振らない条件**（重み0。小さな転は振ってよい）:

- 直前の章で大きな転を入れた（今回当たった転を含む）。
- 作品の最初の 1/8（`序盤の除外_割合`）にある。
- 壊したあとに残るもの・主人公の選択の余地を一つも挙げられない。
- 前提を壊す型だけ: その章より前に伏線を置ける章が無い。

**位置の帯**: 章数を N とする。中心は N×1/4、N×1/2、N×3/4（四捨五入）。作品ごとに一度だけ、三つの中心を同じ幅ずらす。ずらしの候補は章単位の整数 −k〜+k（k = N/16 の切り捨て）で重みはすべて1。k が0なら振らずに0。帯の幅は中心から ±N/8（切り上げ、最低1章）。

**章ごとの確率**: 基準 0.15 に、当てはまる倍率を掛ける。上限 0.9。

| 条件 | 倍率 |
| --- | --- |
| 前の大きな転から3章以上空いている | ×2 |
| 位置の帯の中 | ×2 |
| 平坦な区間の中 | ×1.5 |
| 先送りの溜まりが2 | ×1.5 |

**回数の調停**: 抽選対象の章を前から順に処理する。R は、抽選対象のうちまだ処理していない章（この章を含む）で、振らない条件に当たらない章の数。先の章も、その時点で分かっている転（維持する転と、ここまでに当たった転）に照らして判定する（維持する転の直後の章は R に数えない）。

- C ≥ U → 確率0（振らずに「上限到達」と記録）。
- L − C ≥ R → 確率1（振らずに「下限のため配置」と記録）。
- それ以外は上の確率で振る。当たったら C に1を足す。
- 振らない条件が優先する。最後まで処理して C < L なら、足りない数と理由を作者に報告する（失敗にしない）。
- 見直しの転の行き先が決まらなかったときは、旧配置を維持する案と削除する案の両方を示す。黙って戻したり消したりしない。

**型の重み**: 大きな転が当たった章では `大きな転_型` から型を振る。基準の重みは手順7の「実効の表」から取る。直近3章で使った型は重みを半分にする。振らない条件で外れた型は候補から除く。小さな転は `小さな転_確率` で有無を振り、当たれば `小さな転_型` から振る。

**作品全体の項目**: `作品の約束の破壊`（当たったら序盤のほのめかしの位置を案に含める）、`オチ_回収のしかた`、`オチ_答えの形`、`後味`。振るのは、手順4で「見直し」または「未決」にした項目だけ。「維持」の項目は振らない。

### 7. 振って、すぐ記録する（`rolled`。道具を使わないときの手順）

手順6の道具は、以下をすべて行う。道具を使ったときは、ファイルを読み直して行数と `draw_id` を確かめるところから続ける。

**実効の表**（項目ごとに、どの表から候補を取るか）を、次の順で一つに決める。表どうしを合成しない。

1. `uv run python tools/novel_pick_registry.py --novel novels/<作品> show <list_id>` を実行する（`--novel` は `show` より前に置く）。作品ごとの上書き（`novels/<作品>/pick_registry/work.yaml`）や作業用の `_how_to/pick_registry/` が同じ `list_id` を定義していれば、その `source`・`path` が出る。
2. 出た `source` が標準の `_how_to.example/episode/general/episode_structure_dosing.json` で、作業用の `_how_to/episode/general/episode_structure_dosing.json` があるときは、作業用の同じ `path` を使う。
3. それ以外は、出た `source`・`path` をそのまま使う。
4. 補正の数値（`補正`）は、作業用の JSON があればそちら、無ければ標準から取る。作品だけ回数の範囲を変えるときは、作者の指示として `_meta.md` に書く（手順6）。

候補はその表から読み、補正を当てて JSON の配列にし、重みは「確率」欄に書いて、既存の道具に渡す。**どの項目も `--eval` で振る**（`novel_pick_registry.py pick` で直接振らない。作品ごとの上書きや作業用の表が効かない経路があるため）。

```text
uv run python tools/json_weighted_pick.py --eval '<補正後の候補の JSON 配列>' --seed <個別のシード> --json
```

- 大きな転の有無は `[{"結果":"有","確率":p},{"結果":"無","確率":1-p}]` で振る。確率0／1に固定した章は振らない。
- 補正の要らない項目（オチ・後味など）も、実効の表から読んだ候補をそのまま `--eval` で渡す。
- 出力の `mode` が `weighted` でなければ（重みの欠けで均等に落ちた）、候補の書き方を直して振り直す。

**振ったらすぐ記録する。** 案を作る前に、一回振るごとに `draws.jsonl` へ1行追記する（形式は手順10の表）。確率0／1に固定して振らなかった章も、その時点で1行残す。全部振り終えたら、ファイルを読み直して行数と `draw_id` を確かめる。`draw_id` が確定してから案を作る。作者が案を採らなくても、選択待ちで止まっても、この記録は残す。

**シード**: 作品のシード W を一度だけ決めて `_meta.md` に記録する（作者の指定があればそれ、無ければ任意の整数）。個別のシードは `W:scope:item:attempt` の SHA-256 の先頭8桁を16進数として読んだ値。`attempt` はやり直しの回数（初回0）。

```text
uv run python -c "import hashlib,sys;print(int(hashlib.sha256(sys.argv[1].encode()).hexdigest()[:8],16))" "<W>:ch05:major:0"
```

### 8. 案として見せる

- 提示層で2〜3案を出す。各案は「誰が何をして、何が変わるか」の口語の文（`_how_to.example/synopsis_presentation.md`）。型名・ID・確率・シードは案の本文に書かず、別の枠の設計情報に分ける（`concepts.md`「設計層と提示層」）。
- 各転に、作法として必ず添える: 主たる対象一つ、残るもの、新しい問い、主人公の選択、流れB。前提を壊すなら伏線の位置、作品の約束を壊すならほのめかしの位置。
- `rolled` では、振った結果と案を対応させる（どの `draw_id` から作った案か）。作者が振り直しを求めたら `attempt` を上げて振る。
- 決めるのは作者。承認前に設計・本文を書き換えない。

### 9. 反映する

- 未執筆の章: 作者が採った案を `design_specification.md` の章出来事に反映する。章項の本文は口語の「誰が何をした」、転の型名は章の見出しや `_meta.md`（設計層）に置く。
- 反映したら、変えた章項とその直前・直後の項に**因果検査**を通す（`novel-planning`「章出来事の因果検査（Gate B の外・単独起動）」の手順3〜4と同じ範囲・同じ拘束）。作者が採った案の項は、反映するときに動機を出してよい。それ以外の前後の項を直すときは、単独起動と同じく「いまの文・直す案・根拠の箇所」を示して作者の承認を得てから書く。根拠を挙げられない項は直さず要確認にする。案出し（手順8）の文の形は変えない。
- 執筆済みの章: 出来事が変わるので清書ではできない。加筆・改稿工程として、作者の承認を得て扱う（`concepts.md`「文章の伸縮」、METRON / CHRONOS が ON の作品は `writing_bridge` の経路）。このスキルの中で本文を書き換えない。

### 10. 記録の形式と、採った案の記録

**抽選の記録**（手順6〜7で、振るたびに書く。`rolled` だけ）: `novels/<作品>/_work/structure/draws.jsonl` に1抽選1行で追記する（既存の行は書き換えない）。置き場は `uv run python tools/work_paths.py resolve novels/<作品> structure`（新しい置き場だけの種類。移行の対象外）。振らずに固定した章の行は、`candidates`・`seed`・`result` を null にし、`fixed`（上限到達／下限のため配置／振らない: 理由）を書く。

| 項目 | 内容 |
| --- | --- |
| `draw_id` | 作品内で一意の番号 |
| `at` | 日時（JST） |
| `mode` | `rolled` |
| `scope` | 章・場面（例: `ch05`）。作品全体の項目は `work` |
| `item` | `major`（大きな転の有無）、`major_type`、`minor`、`minor_type`、`band_offset`、`contract_break`、`payoff_mode`、`payoff_answer`、`ending_tone` |
| `list_id` | 使った list_id。`--eval` だけなら `inline` |
| `table_source` | 実際に候補を読んだ表のパス・`path`・`_meta.version`（作品用の表で無ければ null）・ファイルの SHA-256。`show` で出た `registry_dir` と `fragment` |
| `adjustments` | 当てた補正（振らない条件、倍率、直近の抑制） |
| `candidates` | `--eval` に渡した候補の配列全体（順序ごと、重みの欄を含む） |
| `weights_used` | 出力の `weights_used` |
| `seed` | 個別のシード |
| `result` | 出力の `picked`・`index`・`mode` |
| `budget` | `major` のときだけ: L・U・C・R、確率0／1に固定したか。作品の最初の抽選では、維持・見直し・抽選対象の章の一覧も |

確率0／1に固定して振らなかった章も、`result` を空にして `budget` 付きで1行残す。

**採った案の記録**（作者が案を採って反映したとき。全モード）: `_meta.md` の Gate B 記録の **構造方針** 欄（雛形 `_how_to.example/meta.md`）に、方針と決めた経緯、採った案の要約（章ごと。`rolled` ならどの `draw_id` から来たか）、作品全体の項目の決定（オチの回収のしかた・答えの形・後味・作品の約束の破壊と、その決まった箇所）を書く。`rolled` のときは作品のシード W・確率表の版・`draws.jsonl` への参照も書く。次のアレンジでは、この作品全体の項目を手順3の診断で「決定済み」として読む。抽選の結果と採った案は一致しなくてよい。

`none` で意図を確かめて終わったときは、構造方針欄に `none` と、作者が確かめた意図（平坦・オチなしのどれを、何を残すつもりで選んだか）を書く。

**査証ログ**: 作業事実を追記する（`AUDIT_LOG | OFF` の作品は除く）。

## 完了の条件

- 案を示しただけのターンは「案の提示」で止まる。完了とは言わない。`rolled` では、この時点で `draws.jsonl` が保存済みであること（手順7）。
- 抽選の記録を確かめるのは `rolled` で振ったときだけ。`golden`・`diagnose`・`none` では記録を作らず、架空の抽選の記録や回数の範囲（L・U）を作らない。
- モードごとの完了:

  | モード | 完了と言える状態 |
  | --- | --- |
  | `rolled` | 採った案を未執筆の章の設計へ反映し、変えた項と前後に因果検査を通し、`design_specification.md` を Read で読み直し、`draws.jsonl` の行数と、`_meta.md` の構造方針欄（`draw_id` の参照つき）を確かめた |
  | `golden` | 採った案を設計へ反映し、変えた項と前後に因果検査を通し、`design_specification.md` を読み直し、構造方針欄（型名・採った案）を確かめた |
  | `diagnose` | 採った案を設計へ反映し、変えた項と前後に因果検査を通し、`design_specification.md` を読み直し、構造方針欄（採った案）を確かめた |
  | `none` | 作者が意図を確かめ、構造方針欄に `none` と意図を書いて読み直した（設計の変更は無い） |

- 設計を変えたモードでは、報告の行末に `設定資料の一貫性を監査して` を示す（`novel-planning`「Gate B の外での設定改稿」と同じ扱い。監査は実行しない）。
- 執筆済みの章に及ぶ案は、加筆・改稿工程への引き継ぎ（対象章・採った案・承認の有無）を報告して止まる。

## 報告

- モードと、そのモードにした理由（今回の明示／記録／既定）。
- 診断の要約（平坦な区間、未回収の main の約束、植え付け不足、山の位置）。
- 案（提示層）。設計情報（型・確率・シード・`draw_id`）は別の節。
- `rolled` のときだけ: 回数の範囲（L・U）と配置できた数、足りないときは理由。`draws.jsonl` の保存先と行数。
- 作品全体の項目のうち、維持したものと、見直し・未決として扱ったもの。
- 設計へ反映したとき: 因果検査で直した項（章と番号）と項ごとの根拠の箇所、要確認の一覧。
- 工程正本として読んだ葉（因果検査を通したときは `synopsis_presentation.md` も）。
